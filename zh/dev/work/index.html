            一项发现如何流转

            从有人发现问题，到某条基线缩小为止。有两个出口可以让它提前离开这条路径。

            1. 发现问题
            2. 对照 doc/bug-classes.md 检查类别（若是新类别则添加）
            3. 如果该类别涉及验证、分叉选择、证明或 MatMul 前沿 -> 作为 E-CONSENSUS 证据；到此为止 （出口：路径可在此结束）
            4. 在当前最新提交上统计位置数（真实位置少于 3 处：只提交规则） （出口：路径可在此结束）
            5. 清理每一处 + 编写规则（测试、lint 规则或 CI 作业）
            6. 附 fork CI 运行链接的 PR：修复前失败，修复后通过
            7. 由该任务的第二审阅人二次审阅（周三）
            8. 周四批次交给维护者
            9. 合并 -> 看板卡片移动 -> 基线缩小

            最终去向

            拉取请求

            向 release-0.34.17 提交的普通拉取请求，随周四批次发出，并附上它在 fork 上的 CI 运行：修复前失败，修复后通过。

            证据

            针对验证、分叉选择、证明和 MatMul 前沿：在 #464 上提供一个实测结果、一个现成的测试和一段说明。仅在维护者要求时才提交拉取请求。

            运行报告

            一台机器上的一个脚本输出一行结果，由运行者原样粘贴，再加一行说明哪些没有测试。

            出现问题时

            • 关卡变红（某条基线增长，或某个已知失败列表增长）：该任务停止新工作，先修复关卡。
            • 维护者未采纳而关闭的拉取请求绝不重新提交；它要么成为一条证据，要么就此放弃。
            • 负责人与第二审阅人意见不一：由批次协调人决定哪些内容进入批次；如果需要维护者的意见，就把问题写成一行放进周四批次。
            • 与安全相关的发现要通过 btxchain/btx 上 GitHub 的私密漏洞报告（private vulnerability reporting）提交，绝不能发到公开的 issue 或聊天中；登记表只记录其类别，不含细节。
            • 运行者无法复现注明的测试：该拉取请求暂缓，由负责人而不是运行者去调查。
