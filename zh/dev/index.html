成为 BTX 开发者

如何向 BTX 节点软件提交维护者能够合并的拉取请求：写给人，也写给他们使用的 AI 工具。

开始 AI 简报 级别 现状 缺陷类别 任务 流程 关卡 节奏 规则 参与

从哪里开始

开发者中心是本网站 GitHub 代码仓库中的一个文本文件夹。它说明贡献者如何工作；它不代表 btxchain/btx 发言，合并什么由 btxchain/btx 的维护者决定。本页列出要点；细节在文件中，你的 AI 工具可以直接读取。

入门步骤

  1. 阅读开发者中心的首页，面向人类读者。 ↗
  2. 选择一个级别：各级别需要什么，以及第一个小时做什么。 ↗
  3. 把智能体文件交给你的 AI 工具（Claude Code、Cursor、Codex 或其他工具）。 ↗
  4. 学习工作方法：生成、质疑、核实，然后发布。 ↗
  5. 在 Linux、macOS 或 Windows 上构建和测试；测试覆盖率的步骤适用于 Linux。 ↗
  6. 向上游提交拉取请求之前：八个问题和模板。 ↗
  7. 认领一项任务：通过拉取请求，把你的 GitHub 用户名填进它的负责人一行。 ↗
  8. 用测验检查你的配置：十二个答案已知的案例。 ↗

我们如何工作

修复类别，而非个例

每类反复出现的缺陷一个拉取请求：修复机器规则找到的每一处，再加上让该类缺陷保持为零的规则（单元测试、lint 规则或 CI 作业）。

先在 fork 上测量

fork 上的 CI 运行每条类别规则，每个拉取请求都链接其运行记录：修复前失败，修复后通过。每个数字都注明来源以及测量时所在的提交。

负责人与二次审阅

每项任务有一名负责人和一名第二审阅人，两者绝不是同一个人。对于运行类任务，二次审阅是在不同硬件上的一次独立运行。

每项任务都有完成标准

每项任务都有可衡量的完成标准。当关卡 G2（机器检查已开启）、G3（解析器已覆盖）和 G4（缺陷类别已清理）都满足时，整个计划即告完成；此后每周批次缩减为只剩棘轮检查。

给你的 AI 下达简报

三个级别

级别是起点，而不是头衔。要进入下一级：你（或你和你的 AI 工具）通过测验，并且你向上游提交的第一个拉取请求要经过某项任务负责人的二次审阅。

Basic：核实

在拉取请求对应的提交上重跑它注明的测试，或者检查发布压缩包的 SHA-256 以及它能否启动。一台 Linux 机器或 WSL2，大约一小时的准备，无需花钱，机器上不放钱包。

入门简报 ↗

Advanced：团队

负责一项任务（一类缺陷或一个代码领域），并有第二个人检查每个 diff。清理整类缺陷，加上让它保持为零的规则，提交经过测试的拉取请求。需要一台能带测试构建代码的机器、一个 fork，以及每周几个小时。

入门简报 ↗

Core：运行检查

运行其他人所依赖的检查：fork 上的 CI、版本发布资格验证，以及把一周的拉取请求汇总成一批。需要一个启用 GitHub Actions 的 fork，以及每周的时间。

一项发现如何流转

从有人发现问题，到某条基线缩小为止。有两个出口可以让它提前离开这条路径。

  1. 发现问题
  2. 对照 doc/bug-classes.md 检查类别（若是新类别则添加）
  3. 如果该类别涉及验证、分叉选择、证明或 MatMul 前沿 -> 作为 E-CONSENSUS 证据；到此为止 （出口：路径可在此结束）
  4. 在当前最新提交上统计位置数（真实位置少于 3 处：只提交规则） （出口：路径可在此结束）
  5. 清理每一处 + 编写规则（测试、lint 规则或 CI 作业）
  6. 附 fork CI 运行链接的 PR：修复前失败，修复后通过
  7. 由该任务的第二审阅人二次审阅（周三）
  8. 周四批次交给维护者
  9. 合并 -> 看板卡片移动 -> 基线缩小

工作守则

与安全相关的发现要通过 btxchain/btx 上 GitHub 的私密漏洞报告（private vulnerability reporting）提交，绝不能发到公开的 issue、拉取请求、看板卡片或聊天中。登记表只记录类别，不含细节；哪些发现算在内，见防护规则。

规则摘要

  1. 生成、质疑、核实，然后发布：先假定草稿是错的，对照一手来源核实每一项说法；在你亲自运行的命令复现之前，AI 的输出只算线索。
  2. 修复一类缺陷，而不是一处：代码中的每一处，再加上让该类缺陷保持为零的测试、lint 规则或 CI 作业。
  3. 只提交经过测试的修复：修复前失败，修复后通过，并注明提交、平台和命令。说明哪些没有测试。
  4. 验证、分叉选择、证明和 MatMul 前沿不进入 release-0.34.16（btxchain/btx #464 以及同一天关闭的拉取请求，2026 年 11 月 11 日）。这些方面的发现作为证据交给 E-CONSENSUS 任务，而不是作为拉取请求。
  5. 任何内容提交到上游之前，都要由作者以外的第二个人审阅。各任务每周集中提交一次拉取请求，让维护者收到的是一批，而不是源源不断的单个请求。
  6. AI 从不发帖、从不推送，也从不发起拉取请求。这些由你来做，并且要先读完全文和完整的 diff。
  7. 任何地方都不放机密：测试机器、日志、提交或提示词中都不能有密钥、钱包、RPC cookie 或令牌。

每个人的 AI 绝不做的事

每条发布内容都由任务负责人署名；AI 只负责起草。

  1. 绝不自行发帖、评论、推送或发起 PR。负责人先读完全文和 diff。
  2. 绝不向 release-0.34.16 提交涉及以下内容的 PR：validation.cpp、pow.cpp、src/consensus/、script/interpreter.cpp、net_processing.cpp 中的分叉选择或下载调度、node/matmul_trusted_attestations.* 中的规则，或 src/matmul/。这些交给 E-CONSENSUS。
  3. 对登记表中已有的类别，绝不提交只修一处的修复。在当前最新提交上统计该类别；清理它；加上规则。
  4. 绝不把修复放进只在评论中链接的提交里。后续修改一律走 PR。
  5. 没有运行链接或日志、提交 SHA 和平台，绝不声称测试运行过。要么“修复前失败，修复后通过”，要么什么都不说。
  6. 绝不为了让作业变绿而添加桩代码、fail-closed 变通方案、跳过的测试或放宽的超时。
  7. 绝不用 kill -9 停止节点。先停掉所有保活程序或看门狗，备份数据目录，再正常停止节点。
  8. 绝不重新运行已经运行过的基线工具；复用 C1-C3 的结果（plan/plan-data.json 中的数字），只在当前最新提交上重新 grep。
  9. 绝不在测试机或运行者机器上存放密钥、钱包文件、RPC cookie 或令牌；绝不在存有钱包的机器上测试。
  10. 绝不引用私人聊天，提到他人时只用其用户名，绝不给出没有来源的数字。

清理规则与热点文件

  • 清理规则（a）：“未计数”的类别先在当前最新提交上计数；真实位置少于 3 处时，只提交规则
  • 清理规则（b）：清理 PR 只改动本类别的内容；发现的其他问题放进该任务的工作清单或单独的 PR
  • 清理规则（c）：任何清理都不碰 validation.cpp、pow.cpp、src/consensus/、script/interpreter.cpp、分叉选择或 src/matmul/；命中的位置交给 E-CONSENSUS
  • 热点文件（net_processing.cpp、modelnet/helper.cpp、node/matmul_trusted_attestations.*）：没有先提供基于模型的测试或拆分方案，就不提交针对单个事件的 PR

回馈贡献

三个循环让开发者中心保持活力：任务有人认领，陷阱变成经验教训，经验教训变成测验题。

认领一项任务

每项任务都可以认领，包括正在等待负责人的五项。认领就是向本代码仓库提交一个小的拉取请求。

  1. 在 07-lanes.md 中选一项任务：查看它的范围、原因、完成标准和首批工作。
  2. 提交一个拉取请求，把你的 GitHub 用户名填进 07-lanes.md 中该任务的 Owner 一行，以及 plan/lanes.json 的 owner.handle 中。
  3. 第二审阅人填在 second_pass.handle 中。第二审阅人绝不能是负责人本人。
  4. 获得一位 /dev/ 代码所有者（code owner）的批准审阅即可合并。如果 git 让你犯难，就提出来，会有人替你填上。

记录一条经验教训
