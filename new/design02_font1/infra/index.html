03Before you run a node at home

Privacy

  • Your node shows its IP address to every peer it connects to. A node that accepts inbound connections also announces its own address, and peers pass it on.
  • By default btxd asks your router (NAT-PMP or PCP) to open two ports: TCP 19335 for peers and TCP 29447 for the model network, which btxd starts by itself. The model network also looks for peers on your local network over UDP 29448.
  • btxd also checks btx.dev for updates every 30 minutes, directly and not through -proxy, and sends its version, platform, architecture and rollout group. It installs newer signed releases by itself (autoupdateseamless=0 only reports them, autoupdatetelemetry=0 leaves out those details, autoupdate=0 stops the checks).
  • If your address matters, run the node behind Tor (-proxy, -onlynet=onion; the Tor guide advises onlynet=onion only once Tor runs stably) or on a rented server instead. With -proxy, or an -onlynet without ipv4 and ipv6, btxd keeps port 29447 closed and skips the update checks unless you turn them on.
  • On a machine with coins, mining or a signer key, set modelnet=0, natpmp=0 and swapnet=0, as the install checklist says.

Reachability

  • Outbound connections work by default. To accept inbound ones, TCP port 19335 must be reachable: mapped by NAT-PMP, forwarded on the router by hand, or offered as a Tor onion service (-listenonion). With -proxy, the node only listens if you also set -listen=1. Port 29447 is only for the model network; modelnet=0 closes it.
  • A node that only connects out stays in sync and relays to the peers it connects to, but new nodes cannot reach it, so it does not help them sync.
  • To check: btx-cli getpeerinfo shows "inbound": true for peers that connected to you, and btx-cli getnetworkinfo lists your node's localaddresses.

04Before you install a node release

  • Details on check 1

    Community tools such as easynode or snapshots are your own choice to trust; check their signatures.

  • Details on check 2

    Compare the SHA-256 that GitHub shows for each file with "shasum -a 256 <file>" ("sha256sum" on Linux).

  • Details on check 3

    If that matters to you, build the tagged source yourself.

  • Details on check 4

    Checking blocks yourself needs a qualified NVIDIA or Apple GPU. Without one, run a trusted mirror with at least two signers, or the node stops.

  • Details on check 5

    Start from a signed snapshot, and do not run -reindex until a release fixes it.

  • Details on check 6

    With coins, mining or a signer, set the last three to 0.

  • Details on check 7

    Then back up the data directory and wallets.

  • Details on check 8

    Some releases change the rules at a fixed block height; this page shows a countdown when one is coming. Each release also stops working about two years after it was built; current ones in November 2028.

  • Details on check 9

    v0.34.16 has archives for Linux and Linux with CUDA; for Apple Silicon Macs the newest is v0.34.15. There is no official Windows build.

  • Details on check 10

    A node that holds coins, mines or signs belongs on the newest full release.

05How it fits together

Who sends what to whom. A box opens its guide or its card; the numbers on the arrows match the list below the map, and each line of the list names its source in the node software.

The connections in words9

  1. Miners and pools ⇄ Full nodes

    A full node hands out block templates; miners and pools send solved blocks back (getblocktemplate, then a stratum job, then submitblock).

    Source doc/btx-miner-pool-readiness.md:4-5

  2. Full nodes ⇄ Trusted mirrors ⇄ Archive nodes

    Blocks and transactions travel between peers. A node that keeps every block serves the whole chain; a trusted mirror still checks bodies, transactions, scripts and state itself, and for the MatMul work it relies on its signers.

    Source src/protocol.h:504-506 doc/btx-matmul-trusted-rpc-mirrors.md:22-32

  3. SwapNet peers ⇄ BTX peer-to-peer network

    A node started with -swapnet=1 finds other SwapNet nodes over the peer connections it already has: no new port, seed list or hosted service. SwapNet is off by default.

    Source doc/swapnet/OPERATIONS.md:5 src/swapnet/node.cpp:96 src/protocol.h:61-68

  4. Discovery relays → BTX peer-to-peer network

    A discovery relay (-matmulvalidation=relay) is the mode meant for public DNS seeds and addnode hosts. It only hands out peer addresses: it serves no blocks, is no authority on the chain and never asks for or serves signatures.

    Source src/init.cpp:651 src/init.cpp:2134-2136 doc/btx-public-node-bootstrap.md:60-62

  5. Attestation signers → Trusted mirrors

    A signer signs each block whose MatMul work it replayed (messages getmmattest and mmattest). On mainnet a trusted mirror by default accepts that work only with signatures from at least two keys it pinned itself; any peer may pass them on. A node that checks blocks itself never uses them in place of its own check.

    Source src/protocol.h:320-327 doc/btx-matmul-trusted-rpc-mirrors.md:34-38 doc/btx-matmul-trusted-rpc-mirrors.md:94-95 doc/btx-matmul-trusted-rpc-mirrors.md:131-134 doc/btx-matmul-v4.7-gpu-operator-runbook.md:121-125

  6. Snapshot publishers → BTX peer-to-peer network

    A snapshot saves a new node most of the sync: a signed copy of a node's data, or a UTXO snapshot at a height compiled into btxd (loadtxoutset). Check its SHA-256 and signature before you load it. A node holding an attested UTXO snapshot can also offer it to peers over the P2P network.

    Source doc/btx-mining-node-snapshot-runbook.md:76-95 contrib/devtools/README.md:179-182 src/protocol.h:564-567 src/init.cpp:765

  7. Archive nodes → Status page

    The status page measures supply, chain height and network figures from an archive node.

    Source btx-community/README.md:50

  8. Releases → BTX peer-to-peer network

    Release archives are published on the releases page of btxchain/btx. For v0.34.16 there are two, both for Linux x86_64 (one built with CUDA 13), and a SHA256SUMS file; on other platforms the node is built from source.

    Source doc/btx-github-release-automation.md:25-26 release v0.34.16

  9. Releases → Guix rebuilders

    A rebuilder builds a release's tagged source with contrib/guix, attests to the result and verifies other rebuilders' attestations. The v0.34.16 release notes say its Linux binaries need glibc 2.38 or newer and these scripts build against glibc 2.31, so their hashes cannot match a rebuild yet.

    Source contrib/guix/README.md:179-199 contrib/guix/manifest.scm:123 doc/release-notes-0.34.16.md:32-33 release v0.34.16

Found a crash or a security problem?

Report it privately through GitHub private vulnerability reporting on btxchain/btx, as its security policy asks. Never post a crash, a sanitizer report or a crashing input in a public issue, pull request or chat: it can show an attacker how to crash running nodes. SECURITY.md of btxchain/btx names two private ways: GitHub's private vulnerability reporting, and mail to team@btx.dev (ask for the current disclosure key before you send sensitive material).
