Two ways

How do you want to run it?

Run the machine and its software yourself, or let an app install and look after the node software for you.

Choice 1

Run it yourself

You keep a machine running and follow its guide. There are seven roles, from a node at home to a fuzz box in a rack. Each card below says what the network gets, what the machine needs and who to ask.

Privacy and ports

Before you run a node at home

A node talks to strangers on the internet. Know what it shows them and how to make it reachable.

Privacy

  • Peers see your IP address. Your node shows it to every peer it connects to. A node that accepts inbound connections also announces its own address, and peers pass it on.
  • By default, btxd asks your router to open two ports. It uses NAT-PMP or PCP to ask for TCP 19335 for peers and TCP 29447 for the model network, which btxd starts by itself. The model network also looks for peers on your local network over UDP 29448.
  • btxd checks btx.dev for updates every 30 minutes. It does this directly, not through -proxy, and sends its version, platform, architecture and rollout group. It installs newer signed releases by itself. autoupdateseamless=0 only reports them, autoupdatetelemetry=0 leaves out those details, and autoupdate=0 stops the checks.
  • If your address matters, use Tor or a rented server. Run the node behind Tor (-proxy, -onlynet=onion) or on a rented server instead. The Tor guide advises onlynet=onion only once Tor runs stably. With -proxy, or an -onlynet without ipv4 and ipv6, btxd keeps port 29447 closed and skips the update checks unless you turn them on.
  • On a machine with coins, mining or a signer key, turn three things off. Set these, as the install checklist says: 
    modelnet=0
natpmp=0
swapnet=0

Reachability

  • Outbound connections work by default. To accept inbound ones, TCP port 19335 must be reachable: mapped by NAT-PMP, forwarded on the router by hand, or offered as a Tor onion service (-listenonion). With -proxy, the node only listens if you also set -listen=1. Port 29447 is only for the model network; modelnet=0 closes it.
  • A node that only connects out helps less. It stays in sync and relays to the peers it connects to. But new nodes cannot reach it, so it does not help them sync.
  • Check whether peers reach you. btx-cli getpeerinfo shows "inbound": true for peers that connected to you. btx-cli getnetworkinfo lists your node's localaddresses. 
    btx-cli getpeerinfo
btx-cli getnetworkinfo

    Seven roles

    The roles

    Three roles serve the network directly. Four test the node software. Each card says what the network gets, what the machine needs, its guide and who to ask.

    Serve the network · 3 roles

    Network Needs: an always-on computer

    Full node

    What the network gets

    Relays blocks and transactions and keeps the network reachable. With a qualified GPU it checks the MatMul work itself. Without one, run it as a trusted mirror, or it stops syncing.

    Crashes and security problems go privately to the maintainers, never in public →
    What the machine needs
    An always-on computer or small server with an SSD and a steady connection. A GPU is optional.
    Setting for a trusted mirror

    btxd ships no signer keys. Pin at least two signers you trust and set the threshold to 2 (the default is 1). On mainnet it will not start with fewer unless you explicitly override that.

    matmultrustedthreshold=2
    More detail on the full node's validation modes

    The map below names the modes. A node that checks blocks itself runs with -matmulvalidation=consensus, a trusted mirror with -matmulvalidation=trusted, and a discovery relay with -matmulvalidation=relay.

    Network Needs: a large disk

    Archive node and snapshot publisher

    What the network gets

    An archive node keeps every block and serves the whole chain to its peers. The status page measures the chain from archive nodes.

    A snapshot publisher turns a node's data into a signed file that saves a new node most of the sync. A sync from genesis currently stops at block 126,978 (#272), so new nodes start from a snapshot.

    Crashes and security problems go privately to the maintainers, never in public →
    What the machine needs
    A server with a large disk (the whole chain, never pruned, plus room for snapshot files) and an upload link that can serve them.
    Setting

    Keep every block:

    prune=0
    Guide

    The runbook's opening note still calls Epoch A a release candidate. The developers' docs index says it has been live on mainnet since block 185,000.

    Network Needs: a qualified GPU

    Attestation signer

    What the network gets

    Replays the MatMul work of new blocks on a qualified GPU (ExactReplay) and signs the result. Trusted mirrors that pinned its key follow those signatures. A node that checks blocks itself never uses them in place of its own check.

    The developers' docs call this role a GPU archive or attestor.

    Crashes and security problems go privately to the maintainers, never in public →
    What the machine needs

    A GPU that passes btxd's self-qualification in strict-device mode and the whole chain. The machine stays online around the clock. One signing key per machine; never on a miner.

    More detail on GPUs that pass

    The runbook reports RTX 5090 and RTX PRO 6000 passing on CUDA 13.2 with cuBLASLt 13.4. Other cards must pass the same self-test.

    Setting

    Keep the whole chain:

    prune=0
    Guide

    Note

    The runbook's status lines still call Epoch A a release candidate. The developers' docs index says it has been live on mainnet since block 185,000.

    Test the node software · 4 roles

    Testing Needs: a dedicated Linux machine

    Always-on fuzz box

    What the network gets

    A machine that runs automatic tests. It runs BTX's more than 270 fuzz targets day and night and keeps every input that reaches new code, so it finds bugs that need hours of mutation. A short CI run starts from nothing every time.

    Crashes and security problems go privately to the maintainers, never in public →
    What the machine needs

    A dedicated Linux machine or VM (Ubuntu 24.04): many CPU threads, about 2 GB of RAM per fuzzing process, 80 GB of free disk, no GPU.

    Check

    Nothing else on it: no node, wallet, miner or keys.

    Testing Needs: a dedicated Linux server

    CI runner

    What the network gets

    Builds and tests the newest commit of a branch every night and publishes the result, so a break shows up within a day. The status page's operator publishes one such run as job CI-0; it is on the developers' Ongoing work page.

    Crashes and security problems go privately to the maintainers, never in public →
    What the machine needs
    A dedicated Linux server with many threads and tens of GB of free disk. The CI-0 run of 15 Nov took about 70 minutes on 30 threads; a coverage build tree alone takes 27 GB.
    Guide

    Guide coming. Until then: the I-CI pack lists the jobs, the build-and-test page has the recipes, and ci/README.md in the btx tree runs a CI stage locally.

    Testing Needs: Linux with clang

    Sanitizer runs

    What the network gets

    Builds the node with AddressSanitizer and UndefinedBehaviorSanitizer, or with ThreadSanitizer, and runs the tests. Memory and threading bugs that pass silently in a normal build turn into reports.

    Crashes and security problems go privately to the maintainers, never in public →
    What the machine needs
    A Linux machine with clang (clang 20 or newer for ThreadSanitizer), plenty of RAM and threads.
    Setting

    Runs are several times slower, so functional tests get a longer timeout:

    --timeout-factor=4
    Guide
    • Build and test, section 6: Sanitizers ↗ (opens another site)
    Who to ask

    The I-CI lane holds the ASan/UBSan and TSan jobs (CI-2, CI-3). It has no owner yet.

    • Until someone claims it, open an issue in this site's repository ↗ (opens another site)

    Testing Needs: Linux with Guix

    Guix rebuilder

    What the network gets

    Rebuilds a release from its tagged source in a fixed Guix environment, so independent builders can compare hashes and nobody has to trust a single build machine.

    Today rebuilders can only compare with each other, not with the published release.

    More detail on why the hashes differ

    The v0.34.16 release notes say its Linux binaries need glibc 2.38 or newer, while these scripts build against glibc 2.31. The release binaries were not made with them.

    Crashes and security problems go privately to the maintainers, never in public →
    What the machine needs
    A Linux machine with Guix: 16 GB free for the Guix store plus 8 GB per platform you build. More cores build faster.
    Guide

    Guide coming. The scripts are in the btx tree (contrib/guix). Their README is Bitcoin Core's and points at Bitcoin Core's signature repository; this site knows of no BTX one yet.

    Map

    How it fits together

    Who sends what to whom. Each station opens its guide or its card. The numbers on the lines match the list of connections, and each connection names its source in the node software.

    The connections in words

    1. 1

      Connection 1: Miners and pools ⇄ and Full nodes

      A full node hands out block templates; miners and pools send solved blocks back (getblocktemplate, then a stratum job, then submitblock).

      Source for connection 1
      • doc/btx-miner-pool-readiness.md:4-5 ↗ (opens another site)
    2. 2

      Connection 2: Full nodes ⇄ and Trusted mirrors ⇄ and Archive nodes

      Blocks and transactions travel between peers. A node that keeps every block serves the whole chain. A trusted mirror still checks bodies, transactions, scripts and state itself; for the MatMul work it relies on its signers.

      Sources for connection 2
      • src/protocol.h:504-506 ↗ (opens another site)
      • doc/btx-matmul-trusted-rpc-mirrors.md:22-32 ↗ (opens another site)
    3. 3

      Connection 3: SwapNet peers ⇄ and BTX peer-to-peer network

      A node started with -swapnet=1 finds other SwapNet nodes over the peer connections it already has: no new port, seed list or hosted service. In v0.34.16 SwapNet is off by default; the install checklist notes it starts by default from 0.34.17.

      Sources for connection 3
      • doc/swapnet/OPERATIONS.md:5 ↗ (opens another site)
      • src/swapnet/node.cpp:96 ↗ (opens another site)
      • src/protocol.h:61-68 ↗ (opens another site)
    4. 4

      Connection 4: Discovery relays → to BTX peer-to-peer network

      A discovery relay (-matmulvalidation=relay) is the mode meant for public DNS seeds and addnode hosts. It only hands out peer addresses: it serves no blocks, is no authority on the chain and never asks for or serves signatures.

      Sources for connection 4
      • src/init.cpp:651 ↗ (opens another site)
      • src/init.cpp:2134-2136 ↗ (opens another site)
      • doc/btx-public-node-bootstrap.md:60-62 ↗ (opens another site)
    5. 5

      Connection 5: Attestation signers → to Trusted mirrors

      A signer signs each block whose MatMul work it replayed (messages getmmattest and mmattest). On mainnet a trusted mirror by default accepts that work only with signatures from at least two keys it pinned itself; any peer may pass them on. A node that checks blocks itself never uses them in place of its own check.

      Sources for connection 5
      • src/protocol.h:320-327 ↗ (opens another site)
      • doc/btx-matmul-trusted-rpc-mirrors.md:34-38 ↗ (opens another site)
      • doc/btx-matmul-trusted-rpc-mirrors.md:94-95 ↗ (opens another site)
      • doc/btx-matmul-trusted-rpc-mirrors.md:131-134 ↗ (opens another site)
      • doc/btx-matmul-v4.7-gpu-operator-runbook.md:121-125 ↗ (opens another site)
    6. 6

      Connection 6: Snapshot publishers → to BTX peer-to-peer network

      A snapshot saves a new node most of the sync: a signed copy of a node's data, or a UTXO snapshot at a height compiled into btxd (loadtxoutset). Check its SHA-256 and signature before you load it. A node holding an attested UTXO snapshot can also offer it to peers over the P2P network.

      Sources for connection 6
      • doc/btx-mining-node-snapshot-runbook.md:76-95 ↗ (opens another site)
      • contrib/devtools/README.md:179-182 ↗ (opens another site)
      • src/protocol.h:564-567 ↗ (opens another site)
      • src/init.cpp:765 ↗ (opens another site)
    7. 7

      Connection 7: Archive nodes → to Status page

      The status page measures supply, chain height and network figures from an archive node.

      Source for connection 7
      • btx-community/README.md:50 ↗ (opens another site)
    8. 8

      Connection 8: Releases → to BTX peer-to-peer network

      Release archives are published on the releases page of btxchain/btx. For v0.34.16 there are two, both for Linux x86_64 (one built with CUDA 13), and a SHA256SUMS file. On other platforms the node is built from source.

      Sources for connection 8
      • doc/btx-github-release-automation.md:25-26 ↗ (opens another site)
      • release v0.34.16 ↗ (opens another site)
    9. 9

      Connection 9: Releases → to Guix rebuilders

      A rebuilder builds a release's tagged source with contrib/guix, attests to the result and verifies other rebuilders' attestations. The v0.34.16 release notes say its Linux binaries need glibc 2.38 or newer and these scripts build against glibc 2.31, so their hashes cannot match a rebuild yet.

      Sources for connection 9
      • contrib/guix/README.md:179-199 ↗ (opens another site)
      • contrib/guix/manifest.scm:123 ↗ (opens another site)
      • doc/release-notes-0.34.16.md:32-33 ↗ (opens another site)

    Security

    Found a crash or a security problem?

    Report it privately through GitHub private vulnerability reporting on btxchain/btx, as its security policy asks.

    Do not

    Never post a crash, a sanitizer report or a crashing input in a public issue, pull request or chat. It can show an attacker how to crash running nodes.
