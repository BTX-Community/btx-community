Become a BTX dev

How to send pull requests to the BTX node software that the maintainer can merge: for people, and for the AI tools they work with.

Where to begin

The developer hub is a folder of text files in this site's repository on GitHub. It describes how contributors work; it does not speak for btxchain/btx, whose maintainer decides what lands. This page shows the essentials; the files have the detail, and your AI tool can read them directly.

  2. Pick a level: what each one needs, and its first hour. ↗
  3. Give your AI tool (Claude Code, Cursor, Codex or another) the agent file. ↗
  4. Learn the working method: generate, challenge, verify, then publish. ↗

  7. Claim a lane: put your GitHub handle in its owner line, by pull request. ↗

How we work

Classes, not instances

One pull request per recurring bug class: the fix at every site a machine rule finds, plus the rule (a unit test, a lint or a CI job) that keeps the class at zero.

Measure first, on the fork

Fork CI runs every class rule, and each pull request links its run: fails before, passes after. Every number carries its source and the commit it was measured on.

An owner and a second pass

Each lane has one owner and one second-pass reviewer, never the same person. For a run lane, the second pass is an independent run on different hardware.

A done bar for every lane

Every lane has a measurable done bar. The programme is done when gates G2 (machines on), G3 (parsers covered) and G4 (classes swept) hold; then the weekly batch shrinks to the ratchet.

Three levels

A level is a starting point, not a rank. To take on the next one: you, or you and your AI tool, pass the exam, and your first upstream pull request goes through a lane owner's second review.

Basic: verify

Re-run a pull request's stated test at its commit, or check a release archive's SHA-256 and that it starts. A Linux machine or WSL2, about an hour of setup, no spend, no wallet on the machine.

The brief to start from ↗

Advanced: team

Own a lane (a bug class or a code area) with a second person who checks every diff. Sweep the class, add the rule that keeps it at zero, send tested pull requests. A machine that builds the code with tests, a fork, a few hours every week.

The brief to start from ↗

Core: runs

Run the checks others rely on: CI on a fork, release qualification, and collecting the week's pull requests into one batch. A fork with GitHub Actions and time every week.

Lanes

16 lanes, each with a scope and a done bar that says when the work is finished. Owners are listed in the hub; a lane without one is open, and you claim it by pull request. The owner and the second reviewer of a lane are never the same person. Every lane is claimable. 5 have a scope and a done bar but no brief yet, and get no work until someone takes them.

How a finding moves

From the moment someone finds something to the moment a baseline shrinks. Two exits leave the path early.

  1. found
  2. class check against doc/bug-classes.md (add a class if new)
  3. if the class touches validation, fork choice, attestation or the MatMul frontier -> E-CONSENSUS evidence; stop here (an exit: the path can end here)
  4. count sites on the live head (under 3 real sites: file the rule alone) (an exit: the path can end here)
  5. sweep every site + write the rule (test, lint or CI job)
  6. PR with the fork CI link: fails before, passes after
  7. second pass by the lane's reviewer (Wednesday)
  8. Thursday batch to the maintainer
  9. merged -> board card moved -> baseline shrinks

Where it ends up

Pull request

A normal pull request to release-0.34.16, sent in the Thursday batch with its fork CI run: fails before, passes after.

Evidence

For validation, fork choice, attestation and the MatMul frontier: one measured result, one ready test and one paragraph on #464. A pull request only if the maintainer asks for one.

Run report

One script on one machine prints one result line, which the runner pastes unchanged, plus one line that says what was not tested.

When something goes wrong

  • Gate red (a baseline grew, a known-failing list grew): the lane stops new work and fixes the gate first.
  • A pull request the maintainer closed without taking it is never re-filed; it becomes an evidence item or is dropped.
  • Owner and second pass disagree: the batch coordinator decides what goes into the batch, and the question goes into the Thursday batch as one line if the maintainer's view is needed.
  • A security-relevant finding goes through GitHub private vulnerability reporting on btxchain/btx, never into a public issue or a chat; the class goes on the registry without the detail.
  • A runner cannot reproduce a stated test: the pull request waits, and the owner, not the runner, investigates.

Rules of the road

Security-relevant findings go through GitHub private vulnerability reporting on btxchain/btx, never into a public issue, pull request, board card or chat. The registry gets the class without the detail; the guardrails say what counts.

The rules in short

  1. Generate, challenge, verify, then publish: assume the draft is wrong, check every claim against a primary source, and treat AI output as a lead until a command you ran reproduces it.
  2. Fix a class, not one spot: every place in the code, plus the test, lint or CI job that keeps the class at zero.
  3. Tested fixes only: fails before, passes after, with commit, platform and command. Say what was not tested.
  4. Validation, fork choice, attestation and the MatMul frontier stay out of release-0.34.16 (btxchain/btx #464 and the pull requests closed on the same day, 11 November 2026). Findings there go to the E-CONSENSUS lane as evidence, not as pull requests.
  5. A second person who is not the author reviews before anything goes upstream. Lanes send their pull requests together once a week, so the maintainer gets one batch, not a stream.
  6. The AI never posts, pushes or opens a pull request. You do, after reading the full text and the full diff.
  7. No secrets anywhere: no keys, wallets, RPC cookies or tokens on a test machine, in a log, a commit or a prompt.

What each person's AI never does

The person who owns the lane signs every post; the AI drafts.

  1. Never post, comment, push or open a PR on its own. The owner reads the full text and the diff first.
  2. Never open a PR into release-0.34.16 that touches validation.cpp, pow.cpp, src/consensus/, script/interpreter.cpp, fork choice or download scheduling in net_processing.cpp, node/matmul_trusted_attestations.* rules, or src/matmul/. Those go to E-CONSENSUS.
  3. Never file a single-site fix for a class in the registry. Count the class on the live head; sweep it; add the rule.
  4. Never put a fix in a commit linked from a comment. Follow-ups are PRs.
  5. Never claim a test ran without the run link or log, the commit SHA and the platform. "Fails before, passes after" or nothing.
  6. Never add a stub, a fail-closed workaround, a skipped test or a widened timeout to make a job green.
  7. Never stop a node with kill -9. Stop any keeper or watchdog first, back up the datadir, then stop the node cleanly.
  8. Never re-run a baseline tool that already ran; reuse the C1-C3 results (the numbers in plan/plan-data.json) and re-grep only the live head.
  9. Never hold keys, wallet files, RPC cookies or tokens on a test or runner box; never test on the machine that holds a wallet.
  10. Never quote private chats, name people other than by handle, or state a figure without its source.

Sweep rules and hot files

  • Sweep rule (a): a 'not counted' class is counted on the live head first; under 3 real sites, the rule alone
  • Sweep rule (b): a sweep PR changes nothing beyond its class; anything else it finds goes to the lane worklist or its own PR
  • Sweep rule (c): no sweep touches validation.cpp, pow.cpp, src/consensus/, script/interpreter.cpp, fork choice or src/matmul/; hits go to E-CONSENSUS
  • Hot files (net_processing.cpp, modelnet/helper.cpp, node/matmul_trusted_attestations.*): no per-event PR without a model-based test or a split proposal first

Contribute back

Three loops keep the hub alive: lanes get owners, traps become lessons, lessons become exam questions.

Claim a lane

Every lane is claimable, including the five that wait for an owner. A claim is a small pull request to this repository.

  1. Pick a lane in 07-lanes.md: its scope, why, done bar and first tasks.
  2. Open a pull request that puts your GitHub handle in the lane's Owner line in 07-lanes.md and in owner.handle in plan/lanes.json.
  3. A second pass goes in second_pass.handle. The second pass is never the owner.
  4. One approving review from a /dev/ code owner merges it. If git is in your way, ask, and someone enters it for you.
How it works, in the hub ↗

File a lesson

Something in the hub was wrong, missing or cost you an evening? That is a lesson: a one-page record of a trap, so nobody pays for it twice.

  1. Copy the template in lessons/README.md to lessons/YYYY-MM-DD-slug.md.
  2. Fill in what happened, what was done, the rule now, the source, how it was verified (command, commit, platform) and which hub pages change.
  3. Open a pull request. Your AI may draft it; you open it.
  4. One approving review from a /dev/ code owner merges it; the owner of each affected page folds the rule in within a week.

Take the exam

Twelve cases with known answers, from public pull requests and the rules of the hub. Passing it, 11 of 12 with sources, is half of moving up a level.

  1. Give the questions to the person or the AI session being checked, in a clone without exam/answers.md, so the key is never in its context.
  2. Answer every question in the fixed shape: verdict, why, sources.
  3. Grade in a separate session or by hand, with the key.
  4. A question counts when the verdict matches and at least one cited source is one the key names; 11 of 12 pass.
