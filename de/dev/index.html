BTX-Entwickler werden

Wie man Pull Requests für die BTX-Node-Software so vorbereitet, dass der Maintainer sie übernehmen kann: für Menschen und für die KI-Werkzeuge, mit denen sie arbeiten.

Einstieg KI einweisen Stufen Stand Klassen Arbeitsbereiche Ablauf Gates Rhythmus Regeln Mitmachen

Wo anfangen

Der Entwickler-Hub ist ein Ordner mit Textdateien im GitHub-Repository dieser Website. Er beschreibt, wie Mitwirkende arbeiten; er spricht nicht für btxchain/btx, und was übernommen wird, entscheidet dessen Maintainer. Diese Seite zeigt das Wesentliche; die Einzelheiten stehen in den Dateien, und dein KI-Werkzeug kann sie direkt lesen.

Erste Schritte

  1. Die Startseite des Hubs lesen, für Menschen geschrieben. ↗
  2. Eine Stufe wählen: was jede braucht, und ihre erste Stunde. ↗
  3. Dem eigenen KI-Werkzeug (Claude Code, Cursor, Codex oder einem anderen) die Agenten-Datei geben. ↗
  4. Die Arbeitsmethode lernen: entwerfen, anzweifeln, prüfen, dann veröffentlichen. ↗
  5. Unter Linux, macOS oder Windows bauen und testen; die Anleitung für die Testabdeckung gilt für Linux. ↗
  6. Bevor du upstream einen Pull Request öffnest: die acht Fragen und die Vorlage. ↗
  7. Einen Arbeitsbereich übernehmen: deinen GitHub-Namen per Pull Request als verantwortliche Person eintragen. ↗
  8. Das eigene Setup mit der Prüfung testen: zwölf Fälle mit bekannten Antworten. ↗

Wie wir arbeiten

Klassen statt Einzelfälle

Ein Pull Request pro wiederkehrender Fehlerklasse: die Korrektur an jeder Stelle, die eine maschinelle Regel findet, dazu die Regel (ein Unit-Test, eine Lint-Regel oder ein CI-Job), die die Klasse bei null hält.

Erst messen, auf dem Fork

Die Fork-CI führt jede Klassenregel aus, und jeder Pull Request verlinkt seinen Lauf: schlägt vorher fehl, besteht danach. Jede Zahl nennt ihre Quelle und den Commit, an dem sie gemessen wurde.

Verantwortung und Zweitprüfung

Jeder Arbeitsbereich hat eine verantwortliche Person und eine zweite prüfende Person, nie dieselbe. Bei einem Bereich mit Prüfläufen ist die Zweitprüfung ein unabhängiger Lauf auf anderer Hardware.

Abschlusskriterien für jeden Bereich

Jeder Arbeitsbereich hat messbare Abschlusskriterien. Das Programm ist fertig, wenn die Gates G2 (Maschinen laufen), G3 (Parser abgedeckt) und G4 (Klassen bereinigt) erfüllt sind; dann schrumpft das wöchentliche Paket auf den Ratchet.

Drei Stufen

Eine Stufe ist ein Einstieg, kein Rang. Für die nächste braucht es zweierlei: Du, oder du mit deinem KI-Werkzeug, bestehst die Prüfung, und dein erster Upstream-Pull-Request geht durch die Zweitprüfung der verantwortlichen Person eines Arbeitsbereichs.

Basic: nachprüfen

Den angegebenen Test eines Pull Requests an seinem Commit wiederholen oder bei einem Release-Archiv die SHA-256 und den Start prüfen. Ein Linux-Rechner oder WSL2, etwa eine Stunde Einrichtung, keine Kosten, keine Wallet auf dem Rechner.

Das Briefing für den Einstieg ↗

Advanced: im Team

Einen Arbeitsbereich übernehmen (eine Fehlerklasse oder einen Code-Bereich), mit einer zweiten Person, die jeden Diff prüft. Die Klasse an allen Stellen beheben, die Regel ergänzen, die sie bei null hält, getestete Pull Requests schicken. Ein Rechner, der den Code mit Tests baut, ein Fork, ein paar Stunden pro Woche.

Das Briefing für den Einstieg ↗

Core: Prüfläufe

Die Prüfläufe betreiben, auf die sich andere verlassen: CI auf dem eigenen Fork, die Prüfung von Releases und das Sammeln der Pull Requests einer Woche zu einem Paket. Ein Fork mit GitHub Actions und Zeit jede Woche.

Wie ein Befund seinen Weg nimmt

Vom Moment, in dem jemand etwas findet, bis zu dem Moment, in dem eine Baseline schrumpft. Zwei Ausgänge verlassen den Weg früher.

  1. gefunden
  2. Klassenprüfung gegen doc/bug-classes.md (neue Klasse ergänzen, falls es sie noch nicht gibt)
  3. berührt die Klasse Validierung, Fork-Wahl, Attestierung oder die MatMul-Frontier -> Beleg für E-CONSENSUS; hier endet der Weg (ein Ausgang: hier kann der Weg enden)
  4. Stellen am aktuellen Head zählen (unter 3 echten Stellen: nur die Regel einreichen) (ein Ausgang: hier kann der Weg enden)
  5. jede Stelle beheben + die Regel schreiben (Test, Lint-Regel oder CI-Job)
  6. PR mit dem Link zum Fork-CI-Lauf: schlägt vorher fehl, besteht danach
  7. Zweitprüfung durch die prüfende Person des Bereichs (Mittwoch)
  8. Donnerstagspaket an den Maintainer
  9. übernommen -> Board-Karte verschoben -> Baseline schrumpft

Wo es landet

Pull Request

Ein normaler Pull Request an release-0.34.16, verschickt im Donnerstagspaket mit seinem Fork-CI-Lauf: schlägt vorher fehl, besteht danach.

Beleg

Für Validierung, Fork-Wahl, Attestierung und die MatMul-Frontier: ein gemessenes Ergebnis, ein fertiger Test und ein Absatz in #464. Ein Pull Request nur, wenn der Maintainer darum bittet.

Laufbericht

Ein Skript auf einem Rechner gibt eine Ergebniszeile aus, die der Runner unverändert einfügt, dazu eine Zeile, die sagt, was nicht getestet wurde.

Wenn etwas schiefgeht

  • Gate rot (eine Baseline ist gewachsen, eine Liste bekannter Fehlschläge ist gewachsen): Der Bereich nimmt keine neue Arbeit an und repariert zuerst das Gate.
  • Ein Pull Request, den der Maintainer geschlossen hat, ohne ihn zu übernehmen, wird nie erneut eingereicht; er wird ein Beleg oder fällt weg.
  • Verantwortliche Person und Zweitprüfung sind uneins: Die Koordination des Pakets entscheidet, was hineinkommt, und die Frage geht als eine Zeile ins Donnerstagspaket, wenn die Sicht des Maintainers gebraucht wird.
  • Ein sicherheitsrelevanter Befund geht über die private Sicherheitsmeldung von GitHub (Private Vulnerability Reporting) an btxchain/btx, nie in ein öffentliches Issue oder einen Chat; die Klasse kommt ohne Einzelheiten ins Register.
  • Ein Runner kann einen angegebenen Test nicht reproduzieren: Der Pull Request wartet, und die verantwortliche Person, nicht der Runner, geht der Sache nach.

Spielregeln

Sicherheitsrelevante Befunde gehen über die private Sicherheitsmeldung von GitHub (Private Vulnerability Reporting) an btxchain/btx, nie in ein öffentliches Issue, einen Pull Request, eine Board-Karte oder einen Chat. Das Register bekommt die Klasse ohne Einzelheiten; was dazu zählt, sagen die Leitplanken.

Die Regeln in Kürze

  1. Entwerfen, anzweifeln, prüfen, dann veröffentlichen: den Entwurf für falsch halten, jede Aussage an der Primärquelle prüfen und Ergebnisse einer KI als Hinweis behandeln, bis ein selbst ausgeführter Befehl sie bestätigt.
  2. Eine Fehlerklasse beheben, nicht eine Stelle: jede Stelle im Code, dazu der Test, die Lint-Regel oder der CI-Job, der die Klasse bei null hält.
  3. Nur getestete Korrekturen: Der Test schlägt vorher fehl und besteht danach, mit Commit, Plattform und Befehl. Sagen, was nicht getestet wurde.
  4. Validierung, Fork-Wahl, Attestierung und die MatMul-Frontier bleiben aus release-0.34.16 heraus (btxchain/btx #464 und die am selben Tag geschlossenen Pull Requests, 11. November 2026). Befunde dort gehen als Belege an den Bereich E-CONSENSUS, nicht als Pull Requests.
  5. Eine zweite Person, nicht der Autor, prüft, bevor etwas upstream geht. Die Arbeitsbereiche reichen ihre Pull Requests einmal pro Woche gesammelt ein, damit der Maintainer ein Paket bekommt statt eines ständigen Stroms.
  6. Die KI postet nichts, pusht nichts und öffnet keinen Pull Request. Das tust du, nachdem du den ganzen Text und den ganzen Diff gelesen hast.
  7. Keine Geheimnisse, nirgends: keine Schlüssel, Wallets, RPC-Cookies oder Tokens auf einem Testrechner, in einem Log, einem Commit oder einem Prompt.

Was die KI einer Person nie tut

Die verantwortliche Person steht mit ihrem Namen hinter jedem Beitrag; die KI entwirft.

  1. Nie selbst posten, kommentieren, pushen oder einen PR öffnen. Die verantwortliche Person liest zuerst den ganzen Text und den Diff.
  2. Nie einen PR an release-0.34.16 öffnen, der validation.cpp, pow.cpp, src/consensus/, script/interpreter.cpp, die Fork-Wahl oder die Download-Planung in net_processing.cpp, die Regeln in node/matmul_trusted_attestations.* oder src/matmul/ berührt. Das geht an E-CONSENSUS.
  3. Nie eine Korrektur für eine einzelne Stelle einreichen, wenn ihre Klasse im Register steht. Die Klasse am aktuellen Head zählen, alle Stellen beheben, die Regel ergänzen.
  4. Nie eine Korrektur in einen Commit legen, der nur aus einem Kommentar verlinkt ist. Nachträge sind PRs.
  5. Nie behaupten, ein Test sei gelaufen, ohne Link zum Lauf oder Log, Commit-SHA und Plattform. „Schlägt vorher fehl, besteht danach“ oder gar nichts.
  6. Nie einen Stub, einen Fail-closed-Workaround, einen übersprungenen Test oder ein verlängertes Timeout einbauen, um einen Job grün zu bekommen.
  7. Nie eine Node mit kill -9 beenden. Zuerst jeden Keeper oder Watchdog stoppen, das Datenverzeichnis sichern, dann die Node sauber beenden.
  8. Nie ein Baseline-Werkzeug erneut laufen lassen, das schon lief; die Ergebnisse aus C1-C3 wiederverwenden (die Zahlen in plan/plan-data.json) und nur den aktuellen Head neu durchsuchen.
  9. Nie Schlüssel, Wallet-Dateien, RPC-Cookies oder Tokens auf einem Test- oder Runner-Rechner halten; nie auf dem Rechner testen, der eine Wallet hält.
  10. Nie private Chats zitieren, Personen anders als mit ihrem Handle nennen oder eine Zahl ohne Quelle angeben.

Regeln für Durchgänge und heiße Dateien

  • Durchgangsregel (a): Eine „nicht gezählte“ Klasse wird zuerst am aktuellen Head gezählt; bei weniger als 3 echten Stellen nur die Regel
  • Durchgangsregel (b): Ein Durchgangs-PR ändert nichts außerhalb seiner Klasse; alles andere, was er findet, kommt auf die Arbeitsliste des Bereichs oder in einen eigenen PR
  • Durchgangsregel (c): Kein Durchgang berührt validation.cpp, pow.cpp, src/consensus/, script/interpreter.cpp, die Fork-Wahl oder src/matmul/; Treffer gehen an E-CONSENSUS
  • Heiße Dateien (net_processing.cpp, modelnet/helper.cpp, node/matmul_trusted_attestations.*): kein PR pro Einzelereignis ohne vorherigen modellbasierten Test oder Vorschlag zur Aufteilung

Mitmachen

Drei Kreisläufe halten den Hub lebendig: Arbeitsbereiche bekommen Verantwortliche, Fallen werden zu Lektionen, Lektionen werden zu Prüfungsfragen.

Einen Arbeitsbereich übernehmen

Jeder Arbeitsbereich kann übernommen werden, auch die fünf, die auf eine verantwortliche Person warten. Eine Übernahme ist ein kleiner Pull Request an dieses Repository.

  1. Einen Bereich in 07-lanes.md wählen: Umfang, Begründung, Abschlusskriterien und erste Aufgaben.
  2. Einen Pull Request öffnen, der deinen GitHub-Namen in die Owner-Zeile des Bereichs in 07-lanes.md und in owner.handle in plan/lanes.json einträgt.
  3. Die Zweitprüfung kommt in second_pass.handle. Die Zweitprüfung ist nie die verantwortliche Person.
  4. Eine zustimmende Review einer für /dev/ zuständigen Person (Code Owner) führt ihn zusammen. Wenn dir git im Weg ist, frag, und jemand trägt es für dich ein.
So geht es, im Hub ↗

Eine Lektion festhalten

Etwas im Hub war falsch, fehlte oder hat dich einen Abend gekostet? Das ist eine Lektion: eine Seite über eine Falle, damit niemand zweimal dafür zahlt.

  1. Die Vorlage aus lessons/README.md nach lessons/YYYY-MM-DD-slug.md kopieren.
  2. Ausfüllen: was passiert ist, was getan wurde, die Regel ab jetzt, die Quelle, wie es geprüft wurde (Befehl, Commit, Plattform) und welche Seiten des Hubs sich ändern.
  3. Einen Pull Request öffnen. Deine KI darf ihn entwerfen; öffnen tust du ihn.
  4. Eine zustimmende Review einer für /dev/ zuständigen Person führt ihn zusammen; wer für eine betroffene Seite zuständig ist, arbeitet die Regel innerhalb einer Woche ein.
So geht es, im Hub ↗

Die Prüfung ablegen

Zwölf Fälle mit bekannten Antworten, aus öffentlichen Pull Requests und den Regeln des Hubs. Sie zu bestehen, 11 von 12 mit Quellen, ist die Hälfte des Aufstiegs zur nächsten Stufe.

  1. Die Fragen der Person oder KI-Sitzung geben, die geprüft wird, in einem Klon ohne exam/answers.md, damit der Schlüssel nie in ihrem Kontext ist.
  2. Jede Frage in der festen Form beantworten: Urteil, Begründung, Quellen.
  3. In einer getrennten Sitzung oder von Hand mit dem Schlüssel bewerten.
  4. Eine Frage zählt, wenn das Urteil stimmt und mindestens eine genannte Quelle eine des Schlüssels ist; 11 von 12 bestehen.
