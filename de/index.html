Community-Treffpunkt

BTX.community

Eine Community-Seite für alle, die sich für BTX interessieren: was es ist, wie man es mint, wie man einen Node betreibt und wo es Hilfe gibt. Betrieben von Community-Mitgliedern, nicht von einer Firma.

Womit möchtest du anfangen?

Neu bei BTX

BTX ist ein Post-Quanten-Fork von Bitcoin mit fester Höchstmenge und eigenem Proof-of-Work (MatMul). Getragen wird es von einer offenen Community, nicht von einer Firma.

  1. Die offizielle Einführung und Dokumentation lesen. Sie wurde für v0.33.2 geschrieben; neuere Releases weichen teils ab. ↗
  2. Nachsehen, wie es dem Netz gerade geht, verständlich erklärt. ↗
  3. Fragen in den Community-Chats stellen (Discord, Telegram). →
  4. Seed oder privaten Schlüssel nie weitergeben. Niemand aus der Community fragt danach; Direktnachrichten mit "Hilfe" oder "Support" sind Betrug.

Mining

Zum Minen braucht man eine Grafikkarte. Man kann allein gegen den eigenen Node minen und jeden Block behalten oder einem Pool beitreten und regelmäßiger ausgezahlt werden.

  1. Einen Miner aus unserer Linkliste wählen - etwa easyBTX (eine App für Mac und Linux; unter Windows über WSL) oder matador (Open Source). →
  2. Lieber einen kleineren Pool wählen. Findet ein Pool die meisten Blöcke, hängt das Netz an ihm; die Statusseite zeigt die aktuellen Anteile. ↗
  3. Im Schnellstart von matador stehen eine fremde Beispiel-Auszahlungsadresse und zwei Pools, die nicht mehr erreichbar sind. Immer die eigene btx1z-Adresse und einen Pool aus unserer Linkliste eintragen. →
  4. Probleme mit einer NVIDIA-Karte? Die offizielle CUDA-Fehlersuche hilft; Teile davon beschreiben den CUDA-Weg von vor Block 185.000. ↗

Einen Node betreiben

Jeder Node leitet Blöcke weiter und hält das Netz erreichbar. Jeden Block selbst prüft ein Node nur mit einer GPU, die den Selbsttest von btxd besteht. Ohne sie läuft er als Trusted Mirror, der signierten Prüfungen von mindestens zwei Signern folgt; sonst bleibt er stehen. Signer haben die höchsten Anforderungen.

  1. Einfachster Start zu Hause - easynode installiert und überwacht btxd für dich. ↗
  2. Auf einem Server - das offizielle Linux-Release braucht glibc 2.38 oder neuer (Ubuntu 24.04, Debian 13); ein GPU-Node nimmt das Archiv -cuda13 (Blackwell-Karten). Das Pre-Release v0.34.16 hat keinen CUDA-Build, GPU-Nodes bleiben daher auf v0.34.15. Für das aktuelle Release gibt es kein offizielles Windows-Archiv. ↗
  3. In Minuten aufholen mit einem täglich signierten Snapshot. Ein Sync ab Genesis bleibt derzeit bei Block 126.978 stehen (Issue #272). ↗
  4. Node hängt bei einer Höhe? Die Node-Hilfe erklärt jeden bekannten Fall und die Lösung. ↗
  5. Signer (GPU-Attestoren) brauchen eine GPU, die den Selbsttest von btxd besteht, und müssen ständig online sein. Das offizielle CUDA-Archiv deckt Blackwell-Karten (sm_120) ab; andere NVIDIA-Karten brauchen einen eigenen Build und qualifizieren sich womöglich nicht. An das Betreiber-Runbook der Entwickler halten. ↗

BTX-Entwickler werden

Die Node-Software ist Open Source, und jeder kann auf GitHub Pull Requests dafür einreichen. Der Entwickler-Hub erklärt dir und deinem KI-Werkzeug, wie man eine Änderung baut, testet und dokumentiert, damit sie übernommen werden kann, und welche Arbeit offen ist.

  1. Auf der Entwickler-Seite anfangen: Einstieg, Stufen, Testabdeckung und offene Arbeitsbereiche. →
  2. Dem eigenen KI-Werkzeug (Claude Code, Cursor, Codex oder einem anderen) die Agenten-Datei geben. ↗
  3. Die Referenzimplementierung und ihre eigenen Regeln für Agenten. ↗

    Erst prüfen

    Bevor du BTX kaufst oder empfängst

    1. Ein Backup machen, bevor Geld ankommt. In btxd schreibt backupwalletbundlearchive eine verschlüsselte Datei; sie und ihre Passphrase offline und getrennt aufbewahren. Jedes Backup kann deine Coins ausgeben: einfache Exporte sofort, das Archiv nach dem Öffnen. Einmal wiederherstellen, um es zu testen.
    2. Die Empfangsadresse vollständig prüfen, nicht nur Anfang und Ende. BTX-Adressen beginnen mit btx1z.
    3. Zuerst einen kleinen Testbetrag schicken. Mindestens 10 Bestätigungen abwarten, bevor eine Zahlung als endgültig gilt; kurze Reorganisationen der Kette gibt es mehrmals am Tag.
    4. Bevor du eine Börse oder einen OTC-Verkäufer nutzt, prüfen, ob Auszahlungen wirklich funktionieren. Ein Preis auf einer Website ist kein Markt, an dem man verkaufen kann.
    5. Auch andere Coins handeln unter dem Kürzel BTX. Ein Markt gehört nur zu dieser Kette, wenn seine Einzahlungsadressen mit btx1z beginnen.
    6. Ein "Modell-" oder "Referenzpreis" ist eine Schätzung, kein Angebot, an das sich jemand halten muss.
    7. Niemand Seriöses fragt nach deinem Seed. Nachrichten mit Hilfe, "Wiederherstellung" oder garantierten Renditen sind Betrug.

    Bevor du ein Node-Release installierst

    1. Node-Releases nur von github.com/btxchain/btx/releases herunterladen. Community-Werkzeuge wie easynode oder Snapshots vertraust du auf eigene Entscheidung; ihre Signaturen prüfen.
    2. Neuere Releases kommen ohne signierte Prüfsummendatei; die letzte mit SHA256SUMS.asc war v0.34.6. GitHub zeigt auf der Release-Seite eine SHA-256 pro Datei: mit "shasum -a 256 <Datei>" vergleichen (unter Linux "sha256sum").
    3. Das beweist, dass die Datei die von GitHub ist, nicht wer sie gebaut hat. Wenn dir das wichtig ist, den getaggten Quellcode selbst bauen.
    4. Zuerst die Rolle des Nodes festlegen. Blöcke selbst prüfen geht nur mit einer zugelassenen NVIDIA- oder Apple-GPU. Ohne sie als vertrauender Spiegel mit mindestens zwei Signern laufen, sonst bleibt der Node stehen.
    5. Ein neuer Node kann nicht ab Genesis synchronisieren: v0.34.15 und v0.34.16 bleiben bei Block 126.978 stehen. Mit einem signierten Snapshot starten und kein -reindex, bis ein Release das behebt.
    6. Zwei Voreinstellungen bewusst wählen: btxd installiert neuere signierte Releases von btx.dev selbst (autoupdateseamless=0 meldet sie nur, autoupdate=0 prüft gar nicht), und das Modell-Netz lauscht auf Port 29447 (modelnet=0 schaltet es ab).
    7. Vor einem Update mit btx-cli stop anhalten und warten, bis btxd beendet ist; nie hart abbrechen. Dann Datenverzeichnis und Wallets sichern.
    8. Vor dem Update die Release-Notes lesen. Manche Releases ändern die Regeln ab einer festen Blockhöhe; diese Seite zeigt dann einen Countdown. Jedes Release hört außerdem etwa zwei Jahre nach dem Bau auf zu laufen, die aktuellen im November 2028.
    9. Linux-Programme brauchen glibc 2.38 oder neuer (Ubuntu 24.04, Debian 13). v0.34.15 hat Archive für Linux, Linux mit CUDA und Macs mit Apple Silicon; einen offiziellen Windows-Build gibt es nicht.
    10. Pre-Releases (rc und v0.34.16) sind zum Testen. v0.34.16 hat keinen CUDA-Build: Ein GPU-, Mining- oder Signer-Node bleibt auf v0.34.15.
