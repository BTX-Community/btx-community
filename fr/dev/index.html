Devenir développeur BTX

Comment proposer au logiciel de nœud BTX des pull requests que le mainteneur peut fusionner : pour les humains, et pour les outils d'IA avec lesquels ils travaillent.

Par où commencer

Le hub des développeurs est un dossier de fichiers texte dans le dépôt GitHub de ce site. Il décrit la façon de travailler des contributeurs ; il ne parle pas au nom de btxchain/btx, et c'est le mainteneur de btxchain/btx qui décide de ce qui est intégré. Cette page en montre l'essentiel ; les fichiers donnent le détail, et votre outil d'IA peut les lire directement.

Premiers pas

  1. Lire la page d'accueil du hub, écrite pour des humains. ↗
  2. Choisir un niveau : ce que chacun exige, et sa première heure. ↗
  3. Donner le fichier pour agents à votre outil d'IA (Claude Code, Cursor, Codex ou un autre). ↗
  4. Apprendre la méthode de travail : générer, contester, vérifier, puis publier. ↗
  5. Compiler et tester sous Linux, macOS ou Windows ; la procédure de mesure de la couverture est prévue pour Linux. ↗
  6. Avant d'ouvrir une pull request en amont : les huit questions et le modèle. ↗
  7. Prendre en charge un chantier : inscrire votre identifiant GitHub sur sa ligne de responsable, par une pull request. ↗
  8. Vérifier votre configuration avec l'examen : douze cas dont la réponse est connue. ↗

Notre façon de travailler

Des classes, pas des cas isolés

Une pull request par classe de bugs récurrente : le correctif à chaque site que trouve une règle automatique, plus la règle (un test unitaire, une règle de lint ou un job de CI) qui maintient la classe à zéro.

Mesurer d'abord, sur le fork

La CI du fork exécute chaque règle de classe, et chaque pull request renvoie à son exécution : échoue avant, passe après. Chaque chiffre indique sa source et le commit sur lequel il a été mesuré.

Un responsable et une seconde revue

Chaque chantier a un responsable et un second relecteur, jamais la même personne. Pour un chantier d'exécutions de tests, la seconde revue est une exécution indépendante sur un autre matériel.

Un critère d'achèvement pour chaque chantier

Chaque chantier a un critère d'achèvement mesurable. Le programme est achevé quand les contrôles G2 (machines en marche), G3 (parseurs couverts) et G4 (classes balayées) sont satisfaits ; le lot hebdomadaire se réduit alors au cliquet (ratchet).

Briefer votre IA

Collez-le comme premier message d'une nouvelle session dans votre outil d'IA (Claude Code, Cursor, Codex ou un autre). Il lit le fichier pour agents, vous pose les questions du premier lancement et s'arrête au contrôle avant pull request. Tout ce qui quitte la machine, c'est vous qui le faites.

Trois niveaux

Un niveau est un point de départ, pas un grade. Pour passer au suivant : vous, ou vous et votre outil d'IA, réussissez l'examen, et votre première pull request en amont passe par la seconde revue du responsable d'un chantier.

Basic : vérifier

Relancer, à son commit, le test indiqué dans une pull request, ou vérifier le SHA-256 d'une archive de version et s'assurer qu'elle démarre. Une machine Linux ou WSL2, environ une heure d'installation, aucune dépense, aucun portefeuille sur la machine.

Le brief de départ ↗

Advanced : en équipe

Prendre en charge un chantier (une classe de bugs ou une partie du code) avec une seconde personne qui vérifie chaque diff. Balayer la classe, ajouter la règle qui la maintient à zéro, envoyer des pull requests testées. Une machine qui compile le code avec ses tests, un fork, quelques heures par semaine.

Le brief de départ ↗

Core : contrôles

Faire tourner les contrôles sur lesquels les autres s'appuient : la CI sur un fork, la qualification des versions et le regroupement des pull requests de la semaine en un seul lot. Un fork avec GitHub Actions et du temps chaque semaine.

Chantiers

16 chantiers, chacun avec un périmètre et un critère d'achèvement qui dit quand le travail est terminé. Les responsables sont indiqués dans le hub ; un chantier sans responsable est ouvert, et vous le prenez en charge par une pull request. Le responsable et le second relecteur d'un chantier ne sont jamais la même personne. Chaque chantier peut être pris en charge. 5 ont un périmètre et un critère d'achèvement mais pas encore de brief, et ne reçoivent aucun travail tant que personne ne les prend.

16 chantiers sur 16

Chantiers par domaine 8

Chacun couvre une partie du code. E-CONSENSUS prépare des éléments de preuve et ne dépose une pull request que si le mainteneur en demande une. A-NET, A-HELPER, A-SHIELDED, A-PQ et A-GUI ont un périmètre et un critère d'achèvement mais pas encore de brief, et attendent un responsable.

Le parcours d'un constat

Du moment où quelqu'un trouve quelque chose jusqu'à celui où une référence diminue. Deux sorties permettent de quitter le parcours plus tôt.

  1. trouvé
  2. vérification de la classe dans doc/bug-classes.md (ajouter la classe si elle est nouvelle)
  3. si la classe touche la validation, le choix de fork, l'attestation ou la frontière MatMul -> éléments de preuve pour E-CONSENSUS ; s'arrêter là (une sortie : le parcours peut s'arrêter ici)
  4. compter les sites sur la tête actuelle (moins de 3 sites réels : déposer la règle seule) (une sortie : le parcours peut s'arrêter ici)
  5. balayer chaque site + écrire la règle (test, règle de lint ou job de CI)
  6. PR avec le lien de CI du fork : échoue avant, passe après
  7. seconde revue par le relecteur du chantier (mercredi)
  8. lot du jeudi au mainteneur
  9. fusionnée -> carte déplacée sur le tableau -> la référence diminue

Où cela aboutit

Pull request

Une pull request normale vers release-0.34.16, envoyée dans le lot du jeudi avec son exécution de CI sur le fork : échoue avant, passe après.

Preuve

Pour la validation, le choix de fork, l'attestation et la frontière MatMul : un résultat mesuré, un test prêt et un paragraphe sur #464. Une pull request seulement si le mainteneur en demande une.

Rapport d'exécution

Un script sur une machine affiche une ligne de résultat, que le runner colle telle quelle, plus une ligne qui dit ce qui n'a pas été testé.

Quand quelque chose tourne mal

  • Contrôle au rouge (une référence a augmenté, une liste d'échecs connus s'est allongée) : le chantier arrête tout nouveau travail et répare d'abord le contrôle.
  • Une pull request que le mainteneur a fermée sans la retenir n'est jamais redéposée ; elle devient un élément de preuve ou est abandonnée.
  • Le responsable et le second relecteur divergent : la coordination du lot décide de ce qui entre dans le lot, et la question figure sur une ligne du lot du jeudi si l'avis du mainteneur est nécessaire.
  • Un constat touchant à la sécurité passe par le signalement privé de vulnérabilités de GitHub (private vulnerability reporting) sur btxchain/btx, jamais par une issue publique ou un chat ; la classe entre au registre sans le détail.
  • Un runner ne parvient pas à reproduire un test indiqué : la pull request attend, et c'est le responsable, pas le runner, qui enquête.

  1. Générer, contester, vérifier, puis publier : supposer que le brouillon est faux, vérifier chaque affirmation auprès d'une source primaire, et traiter ce que produit l'IA comme une piste tant qu'une commande que vous avez lancée ne l'a pas reproduit.
  2. Corriger une classe de bugs, pas un seul endroit : chaque occurrence dans le code, plus le test, la règle de lint ou le job de CI qui maintient la classe à zéro.
  3. Uniquement des corrections testées : échoue avant, passe après, avec commit, plateforme et commande. Dire ce qui n'a pas été testé.
  4. La validation, le choix de fork, l'attestation et la frontière MatMul restent hors de release-0.34.16 (btxchain/btx #464 et les pull requests fermées le même jour, le 11 novembre 2026). Les constats dans ces domaines vont au chantier E-CONSENSUS comme éléments de preuve, pas comme pull requests.
  5. Une seconde personne, qui n'est pas l'auteur, relit avant que quoi que ce soit parte en amont. Les chantiers envoient leurs pull requests ensemble une fois par semaine : le mainteneur reçoit un lot, pas un flux continu.
  6. L'IA ne publie jamais, ne pousse jamais et n'ouvre jamais de pull request. C'est vous qui le faites, après avoir lu tout le texte et tout le diff.
  7. Aucun secret nulle part : pas de clés, de portefeuilles, de cookies RPC ni de jetons sur une machine de test, dans un journal, un commit ou un prompt.

Ce que l'IA de chacun ne fait jamais

La personne responsable du chantier signe chaque publication ; l'IA rédige.

  1. Ne jamais publier, commenter, pousser ni ouvrir une PR de sa propre initiative. Le responsable lit d'abord tout le texte et tout le diff.
  2. Ne jamais ouvrir de PR vers release-0.34.16 qui touche validation.cpp, pow.cpp, src/consensus/, script/interpreter.cpp, le choix de fork ou la planification des téléchargements dans net_processing.cpp, les règles de node/matmul_trusted_attestations.* ou src/matmul/. Ces sujets vont à E-CONSENSUS.
  3. Ne jamais déposer de correctif pour un site unique d'une classe inscrite au registre. Compter la classe sur la tête actuelle, la balayer, ajouter la règle.
  4. Ne jamais mettre un correctif dans un commit lié depuis un commentaire. Tout complément passe par une nouvelle PR.
  5. Ne jamais affirmer qu'un test a tourné sans le lien vers l'exécution ou le journal, le SHA du commit et la plateforme. « Échoue avant, passe après », ou rien.
  6. Ne jamais ajouter de stub, de contournement fail-closed, de test ignoré ou de délai d'expiration allongé pour faire passer un job au vert.
  7. Ne jamais arrêter un nœud avec kill -9. Arrêter d'abord tout keeper ou watchdog, sauvegarder le répertoire de données, puis arrêter proprement le nœud.
  8. Ne jamais relancer un outil de référence déjà exécuté ; réutiliser les résultats C1-C3 (les chiffres de plan/plan-data.json) et ne refaire le grep que sur la tête actuelle.
  9. Ne jamais garder de clés, de fichiers de portefeuille, de cookies RPC ni de jetons sur une machine de test ou de runner ; ne jamais tester sur la machine qui détient un portefeuille.
  10. Ne jamais citer de chats privés, nommer des personnes autrement que par leur identifiant, ni donner un chiffre sans sa source.

Règles de balayage et fichiers sensibles

  • Règle de balayage (a) : une classe « non comptée » est d'abord comptée sur la tête actuelle ; avec moins de 3 sites réels, la règle seule
  • Règle de balayage (b) : une PR de balayage ne change rien au-delà de sa classe ; tout ce qu'elle trouve d'autre va dans la liste de travail du chantier ou dans sa propre PR
  • Règle de balayage (c) : aucun balayage ne touche validation.cpp, pow.cpp, src/consensus/, script/interpreter.cpp, le choix de fork ou src/matmul/ ; ce qui y est trouvé va à E-CONSENSUS
  • Fichiers sensibles (net_processing.cpp, modelnet/helper.cpp, node/matmul_trusted_attestations.*) : pas de PR par événement sans un test fondé sur un modèle ou une proposition de découpage au préalable

Contribuer en retour

Trois boucles font vivre le hub : les chantiers trouvent des responsables, les pièges deviennent des leçons, les leçons deviennent des questions d'examen.

Prendre en charge un chantier

Chaque chantier peut être pris en charge, y compris les cinq qui attendent un responsable. Une prise en charge est une petite pull request vers ce dépôt.

  1. Choisir un chantier dans 07-lanes.md : son périmètre, sa raison d'être, son critère d'achèvement et ses premières tâches.
  2. Ouvrir une pull request qui inscrit votre identifiant GitHub sur la ligne Owner du chantier dans 07-lanes.md et dans owner.handle de plan/lanes.json.
  3. Le second relecteur s'inscrit dans second_pass.handle ; ce n'est jamais le responsable.
  4. Une revue d'approbation d'un code owner de /dev/ suffit pour la fusionner. Si git vous gêne, demandez, et quelqu'un l'inscrira pour vous.
Comment faire, dans le hub ↗

Consigner une leçon

Quelque chose dans le hub était faux, manquait ou vous a coûté une soirée ? C'est une leçon : une page qui consigne un piège, pour que personne ne le paie deux fois.

  1. Copier le modèle de lessons/README.md vers lessons/YYYY-MM-DD-slug.md.
  2. Remplir : ce qui s'est passé, ce qui a été fait, la règle qui s'applique désormais, la source, comment cela a été vérifié (commande, commit, plateforme) et quelles pages du hub changent.
  3. Ouvrir une pull request. Votre IA peut la rédiger ; c'est vous qui l'ouvrez.
  4. Une revue d'approbation d'un code owner de /dev/ suffit pour la fusionner ; le responsable de chaque page concernée y intègre la règle dans la semaine.

Passer l'examen

Douze cas dont la réponse est connue, tirés de pull requests publiques et des règles du hub. Le réussir, 11 sur 12 avec sources, représente la moitié du passage au niveau supérieur.

  1. Donner les questions à la personne ou à la session d'IA évaluée, dans un clone sans exam/answers.md, pour que le corrigé ne soit jamais dans son contexte.
  2. Répondre à chaque question sous la forme fixée : verdict, justification, sources.
  3. Noter dans une session séparée ou à la main, avec le corrigé.
  4. Une réponse compte comme juste si le verdict concorde et si au moins une source citée figure dans le corrigé ; il faut 11 bonnes réponses sur 12 pour réussir.
