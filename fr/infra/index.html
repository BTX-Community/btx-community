    Faire tourner l'infrastructure de BTX

    Les machines que vous pouvez apporter au réseau : ce que fait chacune, ce qu'il lui faut, son guide et à qui demander, avec une carte qui montre comment elles s'articulent.

    Le faire tourner soi-même

    Vous faites tourner une machine et suivez son guide. Sept rôles, du nœud à la maison à la machine de fuzzing en baie ; chaque carte dit ce que le réseau y gagne, ce qu'il faut à la machine et à qui demander.

    Utiliser une solution gérée

    Une application installe et surveille le logiciel du nœud pour vous, sur une machine qui vous appartient. La machine et sa disponibilité restent votre affaire.

    Application de bureau open source (MIT) de l'équipe easyBTX qui installe et supervise btxd sur la machine que vous avez déjà.

    Avant de faire tourner un nœud chez soi

    Vie privée

    • Votre nœud montre son adresse IP à chaque pair auquel il se connecte. Un nœud qui accepte des connexions entrantes annonce aussi sa propre adresse, et les pairs la relaient.
    • Par défaut, btxd demande à votre routeur (NAT-PMP ou PCP) d'ouvrir deux ports : TCP 19335 pour les pairs et TCP 29447 pour le réseau de modèles, que btxd lance de lui-même. Le réseau de modèles cherche en outre des pairs sur votre réseau local via UDP 29448.
    • btxd interroge aussi btx.dev toutes les 30 minutes pour les mises à jour, directement et sans passer par -proxy, et envoie sa version, sa plateforme, son architecture et son groupe de déploiement. Il installe seul les versions signées plus récentes (autoupdateseamless=0 les signale seulement, autoupdatetelemetry=0 omet ces détails, autoupdate=0 arrête les vérifications).
    • Si votre adresse compte, faites tourner le nœud derrière Tor (-proxy, -onlynet=onion ; le guide Tor conseille onlynet=onion seulement une fois Tor stable) ou plutôt sur un serveur loué. Avec -proxy, ou un -onlynet sans ipv4 ni ipv6, btxd garde le port 29447 fermé et ne cherche pas de mises à jour, sauf si vous les activez.
    • Sur une machine avec des coins, du minage ou une clé de signataire, mettez modelnet=0, natpmp=0 et swapnet=0, comme le dit la liste d'installation.

    Joignabilité

    • Les connexions sortantes fonctionnent par défaut. Pour en accepter d'entrantes, le port TCP 19335 doit être joignable : ouvert par NAT-PMP, redirigé à la main sur le routeur, ou proposé comme service onion Tor (-listenonion). Avec -proxy, le nœud n'écoute que si vous ajoutez -listen=1. Le port 29447 ne sert qu'au réseau de modèles ; modelnet=0 le ferme.
    • Un nœud qui ne fait que se connecter vers l'extérieur reste synchronisé et relaie vers les pairs auxquels il se connecte, mais les nouveaux nœuds ne peuvent pas l'atteindre : il ne les aide donc pas à se synchroniser.
    • Pour vérifier : btx-cli getpeerinfo affiche "inbound": true pour les pairs qui se sont connectés à vous, et btx-cli getnetworkinfo liste les localaddresses de votre nœud.

    À vérifier d'abord

    Avant d'installer une version du nœud

    10 vérifications
    1. Téléchargez les versions du nœud uniquement depuis github.com/btxchain/btx/releases. Faire confiance aux outils de la communauté comme easynode ou les instantanés relève de votre choix ; vérifiez leurs signatures.
    2. Les versions récentes n'ont pas de fichier de sommes de contrôle signé : le dernier SHA256SUMS.asc concernait la v0.34.6, et la v0.34.16 a un SHA256SUMS non signé. Comparez le SHA-256 que GitHub affiche pour chaque fichier avec « shasum -a 256 <fichier> » (« sha256sum » sous Linux).
    3. Cela prouve que le fichier est bien celui de GitHub, pas qui l'a compilé. Si cela compte pour vous, compilez vous-même le code source étiqueté.
    4. Décidez d'abord du rôle du nœud. Vérifier soi-même les blocs nécessite un GPU qualifié NVIDIA ou Apple. Sans lui, faites-le tourner comme miroir de confiance avec au moins deux signataires, sinon le nœud s'arrête.
    5. Un nouveau nœud ne peut pas se synchroniser depuis la genèse : la v0.34.15 et la v0.34.16 s'arrêtent au bloc 126 978. Commencez avec un instantané signé et n'exécutez pas -reindex tant qu'une version n'a pas corrigé le problème.
    6. Quatre réglages : btxd installe seul les versions signées récentes de btx.dev (autoupdateseamless=0 les signale, autoupdate=0 ne vérifie plus) ; le réseau de modèles écoute sur le port 29447 (modelnet=0) ; natpmp ouvre les ports 19335 et 29447 du routeur (natpmp=0) ; SwapNet démarre seul dès 0.34.17 et son échec arrête btxd (swapnet=0). Avec fonds, minage ou signataire : les trois derniers à 0.
    7. Avant une mise à jour, arrêtez le nœud avec btx-cli stop et attendez que btxd se termine ; ne le tuez jamais. Sauvegardez ensuite le répertoire de données et les portefeuilles.
    8. Lisez les notes de version avant de mettre à jour. Certaines versions changent les règles à partir d'une hauteur de bloc fixe ; cette page affiche un compte à rebours quand cela approche. Chaque version cesse aussi de fonctionner environ deux ans après sa compilation ; les actuelles en novembre 2028.
    9. Les binaires Linux nécessitent glibc 2.38 ou plus récent (Ubuntu 24.04, Debian 13). La v0.34.16 a des archives pour Linux et Linux avec CUDA ; pour les Mac Apple Silicon, la plus récente est la v0.34.15. Il n'existe pas de version officielle pour Windows.
    10. Les versions candidates (rc) servent aux tests. Un nœud qui détient des coins, mine ou signe doit tourner sur la dernière version complète.

    Les rôles

    Réseau

    Nœud complet

    Ce que le réseau y gagne
    Relaie blocs et transactions et garde le réseau joignable. Avec un GPU qualifié, il vérifie lui-même le travail MatMul. Sans GPU, faites-en un miroir de confiance, sinon il ne se synchronise plus : btxd n'inclut aucune clé de signataire, épinglez-en au moins deux de confiance et mettez matmultrustedthreshold=2 (1 par défaut). Sur le mainnet, il ne démarre pas avec moins, sauf si vous le forcez.
    Machine
    Un ordinateur ou un petit serveur toujours allumé, avec un SSD et une connexion stable. Le GPU est facultatif.

    Nœud d'archive et éditeur de snapshots

    Ce que le réseau y gagne
    Un nœud d'archive garde chaque bloc (prune=0) et sert toute la chaîne à ses pairs ; la page d'état mesure la chaîne sur des nœuds d'archive. Un éditeur de snapshots fait des données d'un nœud un fichier signé qui épargne à un nouveau nœud l'essentiel de la synchronisation. Depuis la genèse, la synchronisation s'arrête au bloc 126 978 (#272) : les nouveaux nœuds partent d'un snapshot.
    Machine
    Un serveur avec un grand disque (toute la chaîne, jamais élaguée, plus de la place pour les fichiers de snapshot) et un débit montant capable de les servir.

    Signataire d'attestations

    Ce que le réseau y gagne
    Rejoue sur un GPU qualifié le travail MatMul des nouveaux blocs (ExactReplay) et signe le résultat. Les miroirs de confiance qui ont épinglé sa clé suivent ces signatures ; un nœud qui vérifie lui-même les blocs ne les met jamais à la place de sa propre vérification. La documentation des développeurs appelle ce rôle archive GPU ou attestateur.
    Machine
    Un GPU qui réussit l'autoqualification de btxd en mode strict-device, toute la chaîne (prune=0), en ligne jour et nuit. Le runbook indique que les RTX 5090 et RTX PRO 6000 la réussissent avec CUDA 13.2 et cuBLASLt 13.4 ; les autres cartes doivent réussir le même autotest. Une clé de signature par machine ; jamais sur un mineur.

    Machine de fuzzing permanente

    Ce que le réseau y gagne
    Fait tourner jour et nuit les plus de 270 cibles de fuzzing de BTX et garde chaque entrée qui atteint du code nouveau ; elle trouve ainsi des bugs qui demandent des heures de mutation. Une courte exécution de CI repart de zéro à chaque fois.
    Machine
    Une machine Linux ou une VM dédiée (Ubuntu 24.04) : beaucoup de threads CPU, environ 2 Go de RAM par processus de fuzzing, 80 Go de disque libre, pas de GPU. Rien d'autre dessus : ni nœud, ni portefeuille, ni mineur, ni clés.

    Exécutions avec sanitizers

    Ce que le réseau y gagne
    Compile le nœud avec AddressSanitizer et UndefinedBehaviorSanitizer, ou avec ThreadSanitizer, et lance les tests. Les bugs de mémoire et de threads qui passent inaperçus dans une compilation normale deviennent des rapports.
    Machine
    Une machine Linux avec clang (clang 20 ou plus récent pour ThreadSanitizer), beaucoup de RAM et de threads. Les exécutions sont plusieurs fois plus lentes : les tests fonctionnels prennent --timeout-factor=4.

    Recompilation avec Guix

    Ce que le réseau y gagne
    Recompile une version à partir de son code étiqueté dans un environnement Guix fixe : des personnes indépendantes comparent les hachages, nul ne dépend d'une seule machine. Selon les notes de v0.34.16, ses binaires Linux exigent glibc 2.38 ou plus, ces scripts compilent contre glibc 2.31 : ils n'en sont pas issus, et les recompilateurs ne se comparent qu'entre eux.
    Machine
    Une machine Linux avec Guix : 16 Go libres pour le store Guix plus 8 Go par plateforme compilée. Plus de cœurs compilent plus vite.

    Comment tout s'articule

    Qui envoie quoi à qui. Chaque case ouvre son guide ou sa carte ; les numéros des flèches renvoient à la liste sous la carte, et chaque ligne de la liste cite sa source dans le logiciel du nœud.

    Les liaisons en mots
    1. 1

      Mineurs et pools ⇄ Nœuds complets

      Un nœud complet distribue des modèles de bloc ; mineurs et pools renvoient les blocs résolus (getblocktemplate, puis une tâche stratum, puis submitblock).

      Source doc/btx-miner-pool-readiness.md:4-5

    2. 2

      Nœuds complets ⇄ Miroirs de confiance ⇄ Nœuds d'archive

      Blocs et transactions circulent entre pairs. Un nœud qui garde chaque bloc sert toute la chaîne ; un miroir de confiance vérifie toujours lui-même le contenu des blocs, les transactions, les scripts et l'état, et pour le travail MatMul il s'appuie sur ses signataires.

      Source src/protocol.h:504-506 doc/btx-matmul-trusted-rpc-mirrors.md:22-32

    3. 3

      Pairs SwapNet ⇄ Réseau pair-à-pair BTX

      Un nœud démarré avec -swapnet=1 trouve d'autres nœuds SwapNet par les connexions entre pairs qu'il a déjà : pas de nouveau port, pas de liste de seeds, pas de service hébergé. SwapNet est désactivé par défaut.

      Source doc/swapnet/OPERATIONS.md:5 src/swapnet/node.cpp:96 src/protocol.h:61-68

    4. 4

      Relais de découverte → Réseau pair-à-pair BTX

      Un relais de découverte (-matmulvalidation=relay) est le mode prévu pour les seeds DNS publics et les hôtes addnode. Il ne distribue que des adresses de pairs : il ne sert aucun bloc, ne fait pas autorité sur la chaîne et ne demande ni ne sert jamais de signatures.

      Source src/init.cpp:651 src/init.cpp:2134-2136 doc/btx-public-node-bootstrap.md:60-62

    5. 5

      Signataires d'attestations → Miroirs de confiance

      Un signataire signe chaque bloc dont il a rejoué le travail MatMul (messages getmmattest et mmattest). Sur le mainnet, par défaut, un miroir de confiance n'accepte ce travail qu'avec les signatures d'au moins deux clés qu'il a épinglées ; tout pair peut les relayer. Un nœud qui vérifie lui-même les blocs ne les met jamais à la place de sa propre vérification.

      Source src/protocol.h:320-327 doc/btx-matmul-trusted-rpc-mirrors.md:34-38 doc/btx-matmul-trusted-rpc-mirrors.md:94-95 doc/btx-matmul-trusted-rpc-mirrors.md:131-134 doc/btx-matmul-v4.7-gpu-operator-runbook.md:121-125

    6. 6

      Éditeurs de snapshots → Réseau pair-à-pair BTX

      Un snapshot épargne à un nouveau nœud l'essentiel de la synchronisation : une copie signée des données d'un nœud, ou un snapshot UTXO à une hauteur compilée dans btxd (loadtxoutset). Vérifiez son SHA-256 et sa signature avant de le charger. Un nœud qui détient un snapshot UTXO attesté peut aussi le proposer à ses pairs sur le réseau P2P.

      Source doc/btx-mining-node-snapshot-runbook.md:76-95 contrib/devtools/README.md:179-182 src/protocol.h:564-567 src/init.cpp:765

    7. 7

      Nœuds d'archive → Page d'état

      La page d'état mesure l'offre, la hauteur de la chaîne et les chiffres du réseau à partir d'un nœud d'archive.

      Source btx-community/README.md:50

    8. 8

      Versions → Réseau pair-à-pair BTX

      Les archives des versions sont publiées sur la page des releases de btxchain/btx. Pour v0.34.16 il y en a deux, toutes deux pour Linux x86_64 (l'une compilée avec CUDA 13), et un fichier SHA256SUMS ; sur les autres plateformes, le nœud se compile depuis les sources.

      Source doc/btx-github-release-automation.md:25-26 release v0.34.16

    9. 9

      Versions → Recompilateurs Guix

      Un recompilateur compile avec contrib/guix le code étiqueté d'une version, atteste le résultat et vérifie les attestations des autres. Selon les notes de v0.34.16, ses binaires Linux exigent glibc 2.38 ou plus et ces scripts compilent contre glibc 2.31 : leurs hachages ne peuvent donc pas encore correspondre à une recompilation.

      Source contrib/guix/README.md:179-199 contrib/guix/manifest.scm:123 doc/release-notes-0.34.16.md:32-33 release v0.34.16

    Vous avez trouvé un plantage ou un problème de sécurité ?

    Signalez-le en privé via le signalement privé de vulnérabilités de GitHub sur btxchain/btx, comme le demande sa politique de sécurité. Ne publiez jamais un plantage, un rapport de sanitizer ou une entrée qui fait planter dans une issue, une pull request ou un chat publics : cela peut montrer à un attaquant comment faire planter des nœuds en service.
