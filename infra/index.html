    Run BTX infrastructure

    Machines you can give the network: what each one does, what it needs, its guide and who to ask, and a map of how they fit together.

    Run it yourself

    You keep a machine running and follow its guide. Seven roles, from a node at home to a fuzz box in a rack; each card says what the network gets, what the machine needs and who to ask.

    Before you run a node at home

    Privacy

    • Your node shows its IP address to every peer it connects to. A node that accepts inbound connections also announces its own address, and peers pass it on.
    • By default btxd asks your router (NAT-PMP or PCP) to open two ports: TCP 19335 for peers and TCP 29447 for the model network, which btxd starts by itself. The model network also looks for peers on your local network over UDP 29448.
    • btxd also checks btx.dev for updates every 30 minutes, directly and not through -proxy, and sends its version, platform, architecture and rollout group. It installs newer signed releases by itself (autoupdateseamless=0 only reports them, autoupdatetelemetry=0 leaves out those details, autoupdate=0 stops the checks).
    • If your address matters, run the node behind Tor (-proxy, -onlynet=onion; the Tor guide advises onlynet=onion only once Tor runs stably) or on a rented server instead. With -proxy, or an -onlynet without ipv4 and ipv6, btxd keeps port 29447 closed and skips the update checks unless you turn them on.
    • On a machine with coins, mining or a signer key, set modelnet=0, natpmp=0 and swapnet=0, as the install checklist says.

    Reachability

    • Outbound connections work by default. To accept inbound ones, TCP port 19335 must be reachable: mapped by NAT-PMP, forwarded on the router by hand, or offered as a Tor onion service (-listenonion). With -proxy, the node only listens if you also set -listen=1. Port 29447 is only for the model network; modelnet=0 closes it.
    • A node that only connects out stays in sync and relays to the peers it connects to, but new nodes cannot reach it, so it does not help them sync.
    • To check: btx-cli getpeerinfo shows "inbound": true for peers that connected to you, and btx-cli getnetworkinfo lists your node's localaddresses.

    Check first

    Before you install a node release

    10 checks
    1. Download node releases only from github.com/btxchain/btx/releases. Community tools such as easynode or snapshots are your own choice to trust; check their signatures.
    2. Recent releases have no signed checksum file: the last SHA256SUMS.asc was for v0.34.6, and v0.34.16 has an unsigned SHA256SUMS. Compare the SHA-256 that GitHub shows for each file with "shasum -a 256 <file>" ("sha256sum" on Linux).
    3. That proves the file is the one on GitHub, not who built it. If that matters to you, build the tagged source yourself.
    4. Decide the node's role first. Checking blocks yourself needs a qualified NVIDIA or Apple GPU. Without one, run a trusted mirror with at least two signers, or the node stops.
    5. A new node cannot sync from genesis: v0.34.15 and v0.34.16 stop at block 126,978. Start from a signed snapshot, and do not run -reindex until a release fixes it.
    6. Four defaults: btxd installs newer signed releases from btx.dev itself (autoupdateseamless=0 only reports them, autoupdate=0 stops checking); the model network listens on port 29447 (modelnet=0); natpmp opens ports 19335 and 29447 on your router (natpmp=0); SwapNet starts by default from 0.34.17, and a failed start stops btxd (swapnet=0). With coins, mining or a signer, set the last three to 0.
    7. Before an upgrade, stop with btx-cli stop and wait until btxd has exited; never kill it. Then back up the data directory and wallets.
    8. Read the release notes before upgrading. Some releases change the rules at a fixed block height; this page shows a countdown when one is coming. Each release also stops working about two years after it was built; current ones in November 2028.
    9. Linux binaries need glibc 2.38 or newer (Ubuntu 24.04, Debian 13). v0.34.16 has archives for Linux and Linux with CUDA; for Apple Silicon Macs the newest is v0.34.15. There is no official Windows build.
    10. Release candidates (rc) are for testing. A node that holds coins, mines or signs belongs on the newest full release.

    The roles

    Network

    Full node

    What the network gets
    Relays blocks and transactions and keeps the network reachable. With a qualified GPU it checks the MatMul work itself. Without one, run it as a trusted mirror or it stops syncing: btxd ships no signer keys, so pin at least two you trust and set matmultrustedthreshold=2 (default 1). On mainnet it will not start with fewer unless you explicitly override that.
    Machine
    An always-on computer or small server with an SSD and a steady connection. A GPU is optional.

    Network

    Archive node and snapshot publisher

    What the network gets
    An archive node keeps every block (prune=0) and serves the whole chain to its peers; the status page measures the chain from archive nodes. A snapshot publisher turns a node's data into a signed file that saves a new node most of the sync. A sync from genesis currently stops at block 126,978 (#272), so new nodes start from a snapshot.
    Machine
    A server with a large disk (the whole chain, never pruned, plus room for snapshot files) and an upload link that can serve them.

    Network

    Attestation signer

    What the network gets
    Replays the MatMul work of new blocks on a qualified GPU (ExactReplay) and signs the result. Trusted mirrors that pinned its key follow those signatures; a node that checks blocks itself never uses them in place of its own check. The developers' docs call this role a GPU archive or attestor.
    Machine
    A GPU that passes btxd's self-qualification in strict-device mode, the whole chain (prune=0), online around the clock. The runbook reports RTX 5090 and RTX PRO 6000 passing on CUDA 13.2 with cuBLASLt 13.4; other cards must pass the same self-test. One signing key per machine; never on a miner.

    Testing

    Always-on fuzz box

    What the network gets
    Runs BTX's more than 270 fuzz targets day and night and keeps every input that reaches new code, so it finds bugs that need hours of mutation. A short CI run starts from nothing every time.
    Machine
    A dedicated Linux machine or VM (Ubuntu 24.04): many CPU threads, about 2 GB of RAM per fuzzing process, 80 GB of free disk, no GPU. Nothing else on it: no node, wallet, miner or keys.

    CI runner

    What the network gets
    Builds and tests the newest commit of a branch every night and publishes the result, so a break shows up within a day. The status page's operator publishes one such run as job CI-0; it is on the developers page.
    Machine
    A dedicated Linux server with many threads and tens of GB of free disk. The CI-0 run of 15 Nov took about 70 minutes on 30 threads; a coverage build tree alone takes 27 GB.

    Testing

    Sanitizer runs

    What the network gets
    Builds the node with AddressSanitizer and UndefinedBehaviorSanitizer, or with ThreadSanitizer, and runs the tests. Memory and threading bugs that pass silently in a normal build turn into reports.
    Machine
    A Linux machine with clang (clang 20 or newer for ThreadSanitizer), plenty of RAM and threads. Runs are several times slower: functional tests get --timeout-factor=4.

    Testing

    Guix rebuilder

    What the network gets
    Rebuilds a release from its tagged source in a fixed Guix environment, so independent builders can compare hashes and nobody has to trust a single build machine. The v0.34.16 release notes say its Linux binaries need glibc 2.38 or newer, while these scripts build against glibc 2.31: they were not made with them, so today rebuilders can only compare with each other.
    Machine
    A Linux machine with Guix: 16 GB free for the Guix store plus 8 GB per platform you build. More cores build faster.
    Guide
    Guide coming. The scripts are in the btx tree (contrib/guix). Their README is Bitcoin Core's and points at Bitcoin Core's signature repository; this site knows of no BTX one yet.

    How it fits together

    Who sends what to whom. A box opens its guide or its card; the numbers on the arrows match the list below the map, and each line of the list names its source in the node software.

    The connections in words
    1. 1

      Miners and pools ⇄ Full nodes

      A full node hands out block templates; miners and pools send solved blocks back (getblocktemplate, then a stratum job, then submitblock).

      Source doc/btx-miner-pool-readiness.md:4-5

    2. 2

      Full nodes ⇄ Trusted mirrors ⇄ Archive nodes

      Blocks and transactions travel between peers. A node that keeps every block serves the whole chain; a trusted mirror still checks bodies, transactions, scripts and state itself, and for the MatMul work it relies on its signers.

      Source src/protocol.h:504-506 doc/btx-matmul-trusted-rpc-mirrors.md:22-32

    3. 3

      SwapNet peers ⇄ BTX peer-to-peer network

      A node started with -swapnet=1 finds other SwapNet nodes over the peer connections it already has: no new port, seed list or hosted service. SwapNet is off by default.

      Source doc/swapnet/OPERATIONS.md:5 src/swapnet/node.cpp:96 src/protocol.h:61-68

    4. 4

      Discovery relays → BTX peer-to-peer network

      A discovery relay (-matmulvalidation=relay) is the mode meant for public DNS seeds and addnode hosts. It only hands out peer addresses: it serves no blocks, is no authority on the chain and never asks for or serves signatures.

      Source src/init.cpp:651 src/init.cpp:2134-2136 doc/btx-public-node-bootstrap.md:60-62

    5. 5

      Attestation signers → Trusted mirrors

      A signer signs each block whose MatMul work it replayed (messages getmmattest and mmattest). On mainnet a trusted mirror by default accepts that work only with signatures from at least two keys it pinned itself; any peer may pass them on. A node that checks blocks itself never uses them in place of its own check.

      Source src/protocol.h:320-327 doc/btx-matmul-trusted-rpc-mirrors.md:34-38 doc/btx-matmul-trusted-rpc-mirrors.md:94-95 doc/btx-matmul-trusted-rpc-mirrors.md:131-134 doc/btx-matmul-v4.7-gpu-operator-runbook.md:121-125

    6. 6

      Snapshot publishers → BTX peer-to-peer network

      A snapshot saves a new node most of the sync: a signed copy of a node's data, or a UTXO snapshot at a height compiled into btxd (loadtxoutset). Check its SHA-256 and signature before you load it. A node holding an attested UTXO snapshot can also offer it to peers over the P2P network.

      Source doc/btx-mining-node-snapshot-runbook.md:76-95 contrib/devtools/README.md:179-182 src/protocol.h:564-567 src/init.cpp:765

    7. 7

      Archive nodes → Status page

      The status page measures supply, chain height and network figures from an archive node.

      Source btx-community/README.md:50

    8. 8

      Releases → BTX peer-to-peer network

      Release archives are published on the releases page of btxchain/btx. For v0.34.16 there are two, both for Linux x86_64 (one built with CUDA 13), and a SHA256SUMS file; on other platforms the node is built from source.

      Source doc/btx-github-release-automation.md:25-26 release v0.34.16

    9. 9

      Releases → Guix rebuilders

      A rebuilder builds a release's tagged source with contrib/guix, attests to the result and verifies other rebuilders' attestations. The v0.34.16 release notes say its Linux binaries need glibc 2.38 or newer and these scripts build against glibc 2.31, so their hashes cannot match a rebuild yet.

      Source contrib/guix/README.md:179-199 contrib/guix/manifest.scm:123 doc/release-notes-0.34.16.md:32-33 release v0.34.16

    Found a crash or a security problem?

    Report it privately through GitHub private vulnerability reporting on btxchain/btx, as its security policy asks. Never post a crash, a sanitizer report or a crashing input in a public issue, pull request or chat: it can show an attacker how to crash running nodes.
